Karpathy 最近发了一条长帖，讲他怎么用 LLM。不是写代码，不是做 Agent。而是**建知识库**。

我读完之后，当天就动手复刻了一遍。选了「太空经济」这个主题，从零开始，2 小时后建成了一个 27 篇文章的结构化 wiki。

下面我把 Karpathy 的思路拆解清楚，然后用这个真实案例说明每一步到底怎么运作。

## 一个核心原则

> 人不碰 wiki。
> 
> Wiki 是 LLM 的领地。人只负责两件事：**投喂原料**，和**提出好问题**。

这是整个方法论的根基。不是"用 AI 帮你记笔记"，而是**让 LLM 成为知识库的唯一维护者**——采集、编译、索引、查询、回填、自检，全部自动化。

传统知识管理的问题：人写、人分类、人维护，要么三天热度烂尾，要么花在整理上的时间比思考还多。Karpathy 反过来了：人的角色从"整理者"变成"提问者"。

## 五个关键机制

### 机制一：两层分离 raw/ vs wiki/

原始资料丢进 `raw/`，只读不改。LLM 读取后"编译"成结构化的 `wiki/` 文章——每份资料一篇摘要，提取概念写成独立文章，互相做反向链接，自动分类。

**太空经济案例：**我往 raw/ 里丢了 11 份资料——3 份 PDF 报告（Aranca 太空经济、BryceTech 创业投资、IAC 在轨经济论文）、2 篇中文行业分析、以及后续补充的 NASA 碎片报告、FCC 监管文件、可回收火箭分析等。一份都没手动编辑过。LLM 自动编译出 27 篇 wiki 文章。

### 机制二：索引替代 RAG

不需要向量数据库。一个 `MASTER-INDEX.md` 文件列出所有文章的路径和一句话摘要，LLM 读一遍就知道该去翻哪篇文章。

**太空经济案例：**我的知识库 27 篇文章、十几万字，但索引文件不到 2KB。LLM 查询时先读索引定位，再精准读取相关文章。小规模（<500 篇）这比 RAG 更轻、更准、零基础设施成本。

### 机制三：查询结果回填（飞轮核心）

每次查询的结果不是看完就扔，而是**存回 wiki**。这是整个系统的飞轮。

**太空经济案例：**这是最神奇的部分。我的知识库编译完有 13 篇文章。然后我问了两个问题：

第一问：*"中美太空竞赛的核心差异在哪里？"*

LLM 交叉对比了 4 篇 wiki 文章，生成了一份深度分析报告。报告末尾自动建议：应该新建一篇「美国太空产业」文章（之前只有中国的）、一篇中美对比文章，并补充两篇现有文章的内容。回填后，知识库从 13 篇长到 15 篇。

第二问：*"如果太空碎片问题 10 年内得不到有效治理，会如何影响巨型星座和太空经济？"*

LLM 串联了碎片、星座、监管、可回收火箭、经济概览 5 篇文章，生成了一份系统性风险分析。结论：太空经济 1.8 万亿的增长目标面临 20-30% 打折风险，但碎片治理本身是万亿级新赛道。回填后建议新增「凯斯勒综合征」和「太空交通管理」两个条目。知识库长到 27 篇。

> **从 13 篇到 27 篇，不是靠丢新资料，而是靠问问题。**每次探索都在沉淀，越用越厚。这就是回填的复利效应。

飞轮效应：提问 → 研究 → 报告 → 回填 → 知识库自动生长

### 机制四：增量编译

一个 `RAW-REGISTRY.md` 跟踪每份原始文件的编译状态。新文件进来只编译新增的，不用重建整个 wiki。

**太空经济案例：**第一批 5 份资料编译完后，我又补了 6 份（NASA 碎片报告、FCC 监管文件、可回收火箭分析等）。LLM 只处理新增的 6 份，自动新建 4 篇概念文章 + 6 篇来源摘要，同时更新已有文章中的关联链接。

### 机制五：自动 Lint（健康检查）

定期让 LLM 通读全库，找矛盾数据、补缺失环节、发现新的关联文章候选。这是人做不到也没耐心做，但 LLM 天然擅长的维护工作。

**太空经济案例：**可以让 LLM 检查——"卫星通信"文章里说 Starlink 部署了 7968 颗，"巨型星座"文章里说的数字是否一致？"太空投资"里的中国数据和"中国商业航天"里的是否吻合？数据量一大，人根本没法通读全库做交叉验证。LLM 可以。

2 小时，11 份原始资料，最终产出：

| 指标 | 数据 |
|------|------|
| 原始资料 | 11 份（PDF + Markdown） |
| Wiki 概念文章 | 15 篇 |
| 来源摘要 | 11 篇 |

覆盖的主题：太空经济概览、卫星通信、地球观测、太空旅游、在轨经济、巨型星座、中美太空产业、太空投资、可回收火箭、太空碎片、天基太阳能、太空监管、凯斯勒综合征、太空交通管理。

所有文章互相通过双链关联。随时可以继续丢资料、继续提问、继续生长。

## 从脚本到产品：我做了一套 Skill 架构

Karpathy 说这些操作目前是"a hacky collection of scripts"（一堆拼凑的脚本）。我做了一件事：**把他的整套方法论封装成了一组 Claude Code Skills**，让任何人装上就能用。

什么是 Skill？可以理解为 LLM 的"标准化操作手册"。你输入一个指令，LLM 就按预设的流程执行。上面太空经济的案例，就是用这套 Skills 跑出来的。

### 七个 Skill，覆盖全生命周期

| Skill | 做什么 | 对应 Karpathy 的哪个环节 |
|-------|--------|-------------------------|
| `/kb-init` | 一键初始化知识库骨架 | 建目录结构 |
| `/kb-ingest` | 预处理 raw/ 新文件（PDF/Excel/图片 OCR/Word），登记到索引 | Data ingest |
| `/kb-compile` | 将原始资料编译为 wiki 文章，自动建链接和索引 | LLM 编译 wiki |
| `/kb-query` | 对知识库提问，生成结构化报告，自动建议回填 | Q&A + Output |
| `/kb-file` | 将查询结果经确认后回填到 wiki | 输出回填 |
| `/kb-lint` | 六项健康检查（断链、矛盾、孤岛、溯源、覆盖度、空白发现） | Linting |
| `/kb-status` | 仪表盘：文章数、编译率、词数、待处理项 | Extra tools |

kb-skills 架构：7 个 Skill + 底层索引文件共享状态

### 实际使用流程

太空经济案例的完整操作流程：

```
# 第一步：初始化
/kb-init /home/my-kb
# → 自动创建 raw/ wiki/ output/ index/ 目录 + 模板文件

# 第二步：丢资料进去，然后导入
# （手动把 PDF、文章放到 raw/ 目录）
/kb-ingest
# → PDF 自动提取文本，图片 OCR，登记到 RAW-REGISTRY

# 第三步：编译为 wiki
/kb-compile
# → 11 份资料 → 13 篇概念文章 + 来源摘要 + 索引更新

# 第四步：提问
/kb-query "中美太空竞赛的核心差异？"
# → 深度分析报告 + 4 条回填建议

# 第五步：回填
/kb-file
# → 确认后自动新建 2 篇文章，更新 2 篇已有文章

# 第六步：健康检查
/kb-lint
# → 检查断链、矛盾、孤岛，输出修复建议

# 随时查看状态
/kb-status
# → 27 篇文章，11 份资料，编译率 100%
```

每个 Skill 就是一条指令。**从 Karpathy 的"一堆脚本"变成了"打字就能用"**。

### 架构设计的几个关键决策

**1. 状态共享靠 Markdown 文件，不靠数据库。**

所有 Skill 通过 index/ 下的 4 个文件协作：MASTER-INDEX（全局索引）、TOPIC-MAP（主题分组）、RAW-REGISTRY（编译状态）、ONTOLOGY（实体定义）。没有任何外部依赖，一个文件夹就是全部。

**2. 回填是半自动的，不是全自动。**

LLM 建议回填内容，人确认后才执行。这是刻意的设计——全自动回填会导致知识库膨胀失控，半自动让人保持对知识质量的把关权。

**3. 预处理脚本解决非文本文件。**

PDF 用 PyMuPDF 提文字和图片，Excel 用 pandas 转文本，图片用 pytesseract 做 OCR，Word 用 python-docx 提取。LLM 只需要读文本，重活由脚本干。

这套 Skills 已经开源，感兴趣的可以直接用。

## 这件事为什么重要

Karpathy 在帖子最后说：

> "I think there is room here for an incredible new product instead of a hacky collection of scripts."

他在说：**现在所有笔记工具（Notion、Obsidian、Roam）都没解决真正的问题。**

真正的问题不是"怎么记笔记"，而是"怎么让知识**自动积累、自动整理、自动发现关联**"。

人脑不擅长这个。但 LLM 天生擅长。

知识管理的门槛，从此从"勤快不勤快"变成了**"会不会问问题"**。
